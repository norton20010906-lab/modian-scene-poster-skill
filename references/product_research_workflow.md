# 产品资料收集与卖点提炼工作流

目标不是“搜到越多越好”，而是为每条海报声明建立可审计证据链。正式文案只能读取通过核验并写入 `data/products.yaml` 的内容。

## 1. 建立输入事实表

先查看用户图片，分开记录：

- 可见事实：型号文字、设备类别、屏幕、摄像头、边框、安装形态、真实 Logo。
- 用户陈述：用户明确给出的型号、场景偏好或官方参数。
- 不可推断项：识别速度、准确率、容量、活体方式、联网协议、管理平台能力。

图片上的商品宣传文字可以成为线索，但除非来源身份明确，否则不要自动视为官方参数。

## 2. 受控搜索

仅使用精确型号，搜索预算最多 3 个查询：

1. `品牌全称 + 精确型号 + 官方`
2. `site:品牌官网域名 + 精确型号`
3. `精确型号 + 产品说明/参数`（只用于补充发现）

来源优先级：

1. 品牌官网、官方说明书、官方产品页。
2. 官方合作平台或用户提供且身份明确的官方资料。
3. 授权渠道或经销商页面。
4. 媒体报道、聚合页和电商页面。

搜索结果摘要只用于发现页面，不单独作为参数证据。无法打开正文或无法确认主体时，将来源标为 `candidate`，不得被卖点引用。

## 3. 声明级核验

把候选资料整理为声明表：

```json
{
  "claim": "考勤门禁一体化",
  "source_ids": ["official-product-index"],
  "decision": "accepted",
  "reason": "官方产品目录明确将其归类为智能人脸考勤门禁机"
}
```

核验规则：

- 来源必须直接支持该声明，不能从相邻型号迁移参数。
- 参数数字、绝对化描述和比较级必须有型号专属的一手资料。
- 两个来源冲突时采用更高等级来源；无法消解则拒绝该声明。
- 场景偏好只能决定表达角度，不能成为功能证据。
- 视觉事实可支撑外观卖点，但不能支撑软件能力或性能参数。

## 4. 写入产品资料库

每个来源必须包含：

- `id`：稳定且唯一。
- `type`：`official`、`official_partner`、`user_provided`、`reseller` 或 `media`。
- `label`：可读说明。
- `url` 或项目内 `path`。
- `status`：只有 `verified` 能被正式卖点引用。
- `verified_at`：`YYYY-MM-DD`。
- `supports`：该来源实际支持的事实范围。

每条 `selling_points` 必须包含非空 `source_ids`，且引用的所有来源均为 `verified`。至少 3 条卖点通过脚本校验后，型号才可设为 `enabled: true`。

## 5. 从事实到海报文案

按“用户收益 + 已验证能力”提炼，不扩张事实：

- 功能事实：`智能人脸识别`。
- 场景收益：`面向企业入口的刷脸通行体验`。
- 海报卖点：使用资料库固定正文 `智能人脸识别通行`。

标题和副标题可以有商业表达，但不得加入新功能、精确性能或绝对承诺。正文卖点不由模型自由改写，而是通过 ID 从资料库取值。

## 6. 运行记录

每次运行保留 `research.json`，至少包含：

- 查询词与检索日期。
- 检查过的来源及等级。
- 接受、拒绝和待确认的声明。
- 本次实际选用的卖点 ID。
- 未联网时使用的资料库核验日期与降级说明。

这份记录用于复核和维护，不直接出现在海报上。
